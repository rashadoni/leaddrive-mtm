# Учёт времени без интернета: ожидаемое поведение и текущие пробелы

## Что должно происходить

1. Первые вход и подтверждение телефона выполняются при наличии сети. Уже допущенный сотрудник должен иметь возможность открыть собственный рабочий день без сети, включая перезапуск приложения. Срок автономного допуска задаётся явной политикой; серверный отказ нельзя считать сетевой ошибкой.
2. Начало, перерыв, продолжение и окончание сохраняются на телефоне до попытки отправки. Должна работать последовательность START → PAUSE → RESUME → FINISH целиком без сети, а не только одна ожидающая отметка.
3. До ответа сервера интерфейс показывает «Сохранено на телефоне · ожидает отправки». Кадровик не видит ещё не полученные данные. Закрытие приложения не означает отправку.
4. Возврат сети при открытом приложении запускает последовательную отправку. После закрытия — при следующем открытии. Гарантировать отправку из полностью закрытого standalone нельзя: в нём нет фонового сервиса.
5. Для каждой отметки остаются неизменные идентификатор, исходное время, последовательность и собранные в момент действия доказательства. Повторы после потерянного ответа не создают дубль. Сервер сохраняет также время получения и отдельно оценивает неправдоподобные часы/задержку.
6. Координаты можно сохранять лишь при действующем согласии и разрешении ОС. Нет GPS или точности — «Местоположение не подтверждено», а не «Вне филиала». Нельзя подставлять координаты, измеренные позднее при синхронизации. Отзыв согласия должен удалять ещё не отправленные координаты.
7. QR проверяется отдельно от времени. Истёкший или не подтверждённый сервером код не становится доказательством присутствия. Для полноценного автономного подтверждения нужен отдельный проверяемый сервером протокол; телефонным часам доверять нельзя.
8. Отозванная установка, изменившиеся полномочия и конфликт с уже закрытым днём требуют видимого результата/разбора. Сохранённую попытку нельзя молча терять или выдавать за принятый табель. Данные разных аккаунтов и компаний изолированы.

## Что обнаружено в текущей реализации

- Долговечная очередь операций и повтор с прежним ID существуют.
- `store/bootstrap.ts` очищает admission после транспортной ошибки. `AttendanceNavigator` закрывает вкладки без admission; сохранённой автономной лицензии нет.
- Экран блокирует следующий шаг, пока START_PENDING не подтверждён. Полную автономную смену текущий UI не поддерживает.
- `captureAttendanceMark` запрашивает consent онлайн. При неудаче сохраняет отсутствие согласованного location evidence; автономного GPS по сохранённому согласию нет.
- QR живёт60 секунд, причём срок проверяется и на серверном получении. Длительная автономная доставка даёт EXPIRED.
- Привязка — server approval пары account+installationId, созданного и сохранённого приложением. Это не аппаратный ключ/аттестация и не ограничение «один сотрудник — один телефон».
- Эти ограничения не исправлены ослаблением действующих guards. Новая автономная модель требует отдельной реализации и проверки контракта допуска/отзыва/порядка событий.

## Проверки при реализации

- Одна полная смена в авиарежиме; перезапуск между каждым действием; восстановление сети и ровно по одному событию в правильном порядке.
- Потеря ответа после принятия сервером; повтор той же операции без дублей.
- Смена аккаунта, отзыв прав/привязки, истечение допуска, перевод часов и переход даты/часового пояса.
- Согласие отозвано офлайн; GPS выключен, неточен, устарел или помечен mock; координаты не заменяются поздней фиксацией.
- QR истёк до доставки, код чужой компании, повтор кода; отсутствие ложного VERIFIED.
- Сохранённая очередь и понятный результат отказа, включая запрос кадровику на исправление времени.

Фактические PASS/FAIL/NOT RUN ведутся в attendance-device-evidence.json и append-only журнале attendance-standalone-session-log.md. Этот документ описывает требуемое поведение; он не является заявлением о готовности offline.
